1. SUPABASE
Otwórz setup/02_pracownia.sql w zwykłym edytorze tekstu.
Skopiuj CAŁY tekst, wklej do Supabase → SQL Editor → New query i kliknij Run.
To rozszerza już istniejącą tabelę ról, bez usuwania kont. Można wykonać ponownie.
Wynik: „Pracownia gotowa”.

2. GITHUB
Repozytorium MUSI być prywatne, ponieważ zawiera prywatne materiały źródłowe.
GitHub → repozytorium → Settings → General → Danger Zone → Change repository visibility → Private.
Przed zmianą plików zachowaj kopię obecnej wersji (Code → Download ZIP).
Podmień zawartość repozytorium na pliki i foldery z tej paczki (bez samego ZIP-a).
Usuń stare vercel.json, index.html, dist i administracja-lokalna, jeśli pozostały po poprzednich paczkach.
Najważniejsze pliki w głównym katalogu: app.py, requirements.txt, vercel.json, login.html, login.mjs.
Foldery public_site, private_workshop i private_materials zachowaj w całości.
Wszystkie prywatne materiały są serwowane przez Flask dopiero po sprawdzeniu konta i roli.
Nie dodawaj hasła do bazy ani klucza Secret do plików.
Jeżeli pliki prywatne były wcześniej w publicznym repozytorium, zmiana widoczności nie cofnie wcześniejszego dostępu.

5. PRACA
Po zmianie opisów kliknij „Zapisz wersję roboczą w chmurze”.
Aby klienci zobaczyli zmianę, administrator klika „Opublikuj opisy na stronie”.
Przed opuszczeniem raportu kliknij „Zapisz ten raport w chmurze”.
Zapisane raporty i materiały otworzysz z rozwijanej sekcji nad pracownią.
Nie edytujcie tej samej wersji opisów jednocześnie: zapis późniejszy zastępuje wcześniejszy.
Nowe konto tworzysz w Supabase; potem w pracowni nadajesz mu rolę przez User UID.
Twojego osobistego raportu i danych przykładowych nie ma na stronie publicznej.
Materiały źródłowe aktualizuje administrator przez prywatne repozytorium.
